# 0.15 预览发布流程

本页说明发布工具，不表示版本已经合并或发布。新入口是 `.github/workflows/cbm-sec-preview-015.yml`，仅接受本仓库 `main` 的手工触发。默认 `publish=false`，只生成测试产物，不创建标签或 Release。旧 `security-preview.yml` 和原版 CBM 的发行流程保持不变。

## 先完成真实整合

原始候选缺失时不发布。取得两份原始文件后，先安全检查归档，再逐文件整合并完成代码评审。下面的命令直接计算两个文件的 SHA-256；只有与原交接值完全一致时才生成记录，已有记录不会被覆盖：

```sh
python3 security/preview_release.py candidate-receipt \
  --source /path/to/cbm-sec-argument-origins-source.tar.gz \
  --validation /path/to/cbm-sec-argument-origins-validation.json \
  --output docs/releases/0.15.0-candidate-receipt.json
python3 security/preview_release.py check-source
```

记录只证明输入文件哈希匹配，不证明候选 Git 树、差异整合、漏洞关系或测试已经通过。不得手填哈希冒充实际核验。本次不会创建空白导出器、占位测试或假的记录来满足门禁。记录和完整候选配套须进入经评审的提交；原始压缩包不上传到发布仓库。

源码预检查要求普通实参示例、专项、导出器、资源与导出测试、受控 Java 参考及记录存在，并核对内部版本 `0.15.0-preview.1`。这只是最低文件完整性检查，不能替代原候选的逐文件整合审查或完整回归。

## 正常合并后再触发

先完成真实 DCO 和全部必要检查，通过正常 PR 合并。发布输入为完整的 40 位合并提交和对应 PR 编号，提交必须等于此次从 `main` 触发的工作流版本。不会自动合并、强制更新分支或补签来源声明。

发布前和准备公开前使用 GitHub API 读取已合并 PR 及其最后 head 的检查。只接受本仓库、目标为 `main`、合并提交与输入一致的非草稿 PR。按工作流文件路径检查 PR、CodeQL、DCO、安全回归和三个框架参考任务；缺失、失败、取消、跳过或仍运行均停止，不能用旧 head 或旧成功任务替代新任务。分页结果必须完整读取。

由于文件须先进入默认分支，这个手工入口不能在当前未合并的草稿上直接完成真实发布。新增工作流的存在不等于入口已经实际运行。

## 固定提交重新构建

校验通过后依次执行文档检查、Clang 地址/未定义行为/泄漏检查、GCC 严格构建和完整安全专项，以及既有安全与依赖完整性检查。构建过程中不执行任意被审计项目。

`security/preview_release.py package` 要求干净的固定提交、真实测试日志和 Linux x86_64。日志必须包含全部现有专项，各组有实际执行数和成功结论；缺组、重复、零项或跳过会失败，不以历史 1,156 项作为本次执行证明。

两个程序的版本和构建指纹分别核验：命令行程序读取 `--version`；MCP 使用空的固定快照核对初始化版本、快照信息和十二工具集合。两者须与该提交的源码指纹一致。

平台包按明确的已跟踪路径收集程序、中文说明、技能、受控样例和许可证。源码使用该提交的 `git archive`，不收集 `.git`、凭据或本地缓存。随包示例实际调用打包的程序；只声明 Linux x86_64，不因上游 CI 通过而增加平台声明。

## 草稿、回读、公开

发布附件为源码包、Linux x86_64 程序包、`BUILD_INFO.json`、`TEST_RESULTS.json`、`DEMO_RESULTS.json`、`CANDIDATE_RECEIPT.json`、`RELEASE_NOTES.md` 和 `SHA256SUMS`，共八项。校验清单覆盖其余七项，回读时还比较校验清单自身的字节。

公开步骤单独持有仓库内容写权限。创建前再次核对 PR、检查和标签；仅当标签及 Release 不存在时创建新标签和草稿。上传不使用覆盖选项。草稿的全部附件重新下载后，核对名称集合、实际字节哈希和提交身份，才设置 `draft=false`、`prerelease=true`、`make_latest=false`。公开后使用另一个空目录再次下载，核对校验清单及全部附件字节，并重新读取附件数量与名称集合、标签目标及发布状态；全部一致才输出完成结果。

上传或草稿回读失败时保留草稿，停止公开。公开后的回读失败时，Release 可能已经可见，但核验尚未完成；脚本不输出 `published=true` 的完成结果，也不自动回滚或删除远程内容。两种情况都应报告已创建的标签、Release 编号、已执行步骤和失败位置。不删除旧附件、不移动标签、不把重试变成覆盖已有版本；此入口不自动恢复已有版本。

## 验证发布工具本身

```sh
python3 tests/security/test_preview_release.py
make docs-check
```

专项中的元数据、模拟 GitHub API 和打包测试仓库均为显式测试夹具，不连接真实 GitHub，不使用令牌，不创建真实标签或 Release。普通实参、资源或导出的实际功能仍由各自原始专项验证。实际发布必须使用正常流水线，不能将模拟成功当作远程交付。
